Phase 2: Steam Logic, Security & Match Analytics
2.1 SDA & 2FA Integration
The bot must use the shared_secret stored in the database to generate login codes.
Library: steampy or a custom implementation of the Steam TOTP algorithm.
Function: generate_steam_guard_code(shared_secret)
Purpose: To provide the 5-digit code to the buyer only when they request it via /code.
2.2 Match Result Tracking (The "Loss" Detector)
The bot needs to monitor the account's match history to know when to terminate the rental.
API: OpenDota API (free and fast) or official Steam Web API.
Logic:
Fetch the most recent match for the steam_id_64.
Check radiant_win and the player's team to determine Win or Loss.
Leaver Status: Check if the player abandoned the game. If leaver_status > 0, treat it as a Loss/Immediate Termination.
MMR/Rank Update: After each match, update the mmr and rank in the database.
2.3 Security Operations (The "Emergency Reset")
When a loss is detected or a rental ends, the bot must secure the account immediately.
Session Revoke: Use Steam Web API to de-authorize all other devices (Logout from all).
Password Change: (Optional but recommended) Automated password rotation to ensure the buyer can no longer log in.
Sanitization: Reset the Steam profile (Name, Avatar, Privacy Settings) to a "clean" state for the next customer.

Phase 5: The Orchestrator, Error Handling & Deployment
5.1 The Master Orchestrator (main.py)
Since you have multiple tasks running at once (monitoring FunPay orders, checking Steam matches, and responding to Telegram commands), you must use an asynchronous event loop.
Task 1: Telegram Bot Polling (Aiogram).
Task 2: FunPay Order Monitor (Polling every 30–60s).
Task 3: Steam Match Monitor (Checking active rentals every 5–10 mins).
Task 4: Currency Updater (Updating exchange rates every 6 hours).
5.2 Robust Error Handling
A single error (like a FunPay timeout) should not crash the whole bot.
Retry Logic: If an API call fails, the bot should wait and try again (Exponential Backoff).
Graceful Shutdown: If you stop the bot, it should save the current state and close DB connections properly.
5.3 Deployment (Dockerizing)
To ensure the bot runs exactly the same on your PC and your Server (VPS), we will use Docker.
Docker Compose: One container for the Python Bot, one for the PostgreSQL database.

Phase 7: Resilience, Stealth & Autonomous Maintenance

Using the same Steam Web API key for 50+ accounts is a "red flag" for Valve.

Jitter Logic: Instead of a fixed 60-second check, implement "Jitter." The bot waits for 60 + random.randint(-15, 45) seconds.
Work Hours: Implement a "Sleep Mode" in settings. You can set the bot to be less active or "Offline" during specific hours to mimic a human sleeping.

FunPay occasionally changes its website layout, which can "break" simple bots.
Feature: Centralized Selector Map. Instead of hardcoding "Click button with ID 'submit'", store these in a configuration file.
Benefit: If FunPay updates their site, you only change one line in your config, and the whole bot works again without a full code rewrite.
7.4. Automatic Log Rotation & DB Cleanup
Running a bot 24/7 generates massive amounts of data.
Maintenance: Implement an automatic cleanup task that archives logs older than 30 days and compresses old order history to keep the database fast.

Fail2Ban: Automatically block IP addresses that try to brute-force your SSH login.
